# Portfolio Direction

## Purpose

This repository is being built as a long-term record of Hanshit Singh's growth from computer science foundations into product and UX/UI design.

The goal is not to make the portfolio look artificially polished. It should show real work, clear decisions, honest limitations, and measurable improvement over time.

## Three-Year CSE Foundation

The current phase focuses on building strong technical fundamentals through practical work:

- C programming and programming fundamentals
- JavaScript, HTML and CSS
- Git and GitHub workflow
- Core computer science and networking
- Browser-based applications and student tools
- AI experiments with clear source-of-truth boundaries
- Validation, accessibility, testing and security-conscious development

Projects should demonstrate what was actually built, why it was built, what was learned, and what remains to improve.

## Next Phase: B.Des / UX and Product Design

The portfolio should be ready to grow naturally into a design portfolio as formal UX/UI study begins. Future work can add:

- User and problem research
- Information architecture
- User flows
- Wireframes
- UI systems and components
- Prototyping
- Accessibility
- Usability testing
- Design systems
- Product thinking and iteration
- Evidence-based case studies

Design work should be connected to real problems rather than added as decoration to existing developer projects.

## Career Positioning

The intended long-term profile is a person who can understand both the technical constraints of software and the needs of people using it.

A useful progression is:

`Learn → Build → Solve → Understand users → Design → Test → Improve`

The portfolio should therefore preserve technical credibility while gradually increasing product and UX evidence.

## Quality Rules

1. Prefer authentic student work over generic AI-generated claims.
2. Use natural language that describes actual decisions and outcomes.
3. Never invent metrics, users, research findings, deployments, or production status.
4. Preserve useful existing projects and learning evidence unless there is a clear reason to replace them.
5. When an old implementation is flawed, restore the useful capability with a better implementation instead of blindly reverting the code.
6. Keep security, accessibility, responsive behavior and maintainability part of the engineering standard.
7. Visual effects should support hierarchy and interaction, not distract from the work.
8. Separate verified evidence from planned or experimental work.
9. Keep the portfolio understandable to both technical recruiters and future design/product recruiters.
10. Each major project should eventually explain: problem, role, approach, implementation/design decisions, verification, limitations, and next iteration.
